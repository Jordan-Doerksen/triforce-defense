Triforce-Defense · how this repo gets built · design-first 0.1.39

Interview every add. Lock before code. Build one domain at a time, checked against all of it.

Every request is interviewed and every decision is locked in one manifest before anything is built. The architecture map names every domain and its config file on one page. Then the build goes one domain at a time, smallest working slice first, and each chunk is cross-checked against the manifest, the map and every other subsystem before the next one starts.

This page exists because a reader saw the word chunk and assumed "interview one department, build it end to end, move to the next." The kit's own phrase for a chunk is "one domain at a time," so the misread is understandable, and the docs never said in plain words what stops that failure. Now they do. The method is the design-first kit; this page describes it as this repo uses it.

The shape of it

Two ways to split a build. The left one is the thing people have been burned by. The right one is what the kit does.

The order

These are the eight steps of the kit's own overview chart, with the clause ids it uses, in words that fit any project. The italic line under a step maps it to the admin-app example the reader gave.

  1. Interview every add. GATE-01 · OWN-04 · OWN-10 · GATE-15 However detailed the request, it is an opening position, not a spec. Restate it, split it into elements, and give every element one verdict: approve, redact, add or flavour. Name what it conflicts with in the manifest and state the cost. Rank each decision and research it in proportion. Then ask only the real forks, one question at a time, with the recommended option first and a reason on every option. Facts about the environment are the agent's job to find, never the owner's to supply. The pass ends when no branch is left silently assumed. This is "meet with every department and ask what they need," except the agent reads the scars first and asks only what only the owner can decide.
  2. Lock the manifest and draw the map. DES-01 · DES-02 Each answer goes into DECISIONS.md with its chosen answer, rationale, date locked, what it affects and its change rule. ARCHITECTURE.md is one page and names every domain with its entry point and its config file. Nothing is coded until its decisions are locked here, and a later change is a Change Request, never drift. This is the list of every menu and every service, agreed before any page exists.
  3. Stakes? Then the design gate. GATE-08 · GATE-09 When a wrong output costs money, safety or someone's trust, write the spec and the manifest first and send them for an adversarial gap review before the repository exists. A review that finds nothing is a failed review. The gate clears when every finding is resolved or recorded, and while it is open the guard refuses every source write. A game skips this step. The payroll module gets this pass. The staff directory does not.
  4. Build one slice of one chunk. DES-05 · DES-04 · DES-06 A chunk is one domain. Build the smallest slice of it that works, edit only that chunk's files, and put every tunable value in that domain's config. Several files that serve one decision are one agent's job. Independent decisions can run in parallel; files cannot. This is the listing pages with mock data: one domain, read-only, no forms yet.
  5. Inner gate, after every small change. GAME-12 Run the repository's verify gate, stop, say what changed and what it proves, and wait. If it fails or the owner rejects the slice, back to step 4.
  6. Outer gate, at every chunk boundary. GATE-05 · GATE-07 Cross-check the chunk against the manifest, the map, the existing subsystems, the config, the tests and the core goal. End with Proceed, yes or no. Check the Definition of Done. Update the documents. After parallel agents, start one more with the manifest and the whole diff. If Proceed is no, back to step 4. This is the review with the departments, except the first reviewer is the map itself.
  7. Change Request, if a locked decision must change. GATE-06 Write the change, the reason, the affected areas, the risk, the required updates and the final decision. The owner decides. Yes adds a dated row to the Change Log and goes back to step 2 for the updates. No leaves the decision standing, and the work changes to agree with it. This is "two chunks ago I set a detail that now breaks," caught in the manifest before the code.
  8. Next chunk, or done. Update the build timeline and the hand-off. For the next chunk, back to step 1 for each decision it still needs, or straight to step 4 when its decisions are already locked.

The five loops

Each one lands on a cheaper step than the one that failed. That is what makes a wrong answer survivable.

Married

Three things the charts make visible that the prose does not. The verdict is per element, so one redact does not throw away the rest of the request. The lock is the gate, so "is this built yet?" has a yes-or-no answer in one file. And every loop lands on a cheaper step than the one that failed.

The words, and what they are not

Most misreads of this method come from loading a familiar meaning onto one of these. Each one is defined here with the meaning it does not carry.

Interview
The agent interviewing the request, with the owner. Restate it, split it into elements, give each a verdict, name the conflicts, state the cost, then ask the real forks one question at a time. Facts about the disk or the environment are the agent's to find, never the owner's to supply. a round of stakeholder interviews. Not requirements gathering. Nothing is collected and handed to a build team.
Verdict
One of four, on every element of a request: approve, redact, add or flavour. Silence is not approval. Full approval is said out loud.
Chunk
One domain, built after every decision is locked and every domain is already on the map. A chunk ends at the outer gate, where it is cross-checked against the manifest and every other subsystem. one department built end to end. Not a sprint. Not a time box.
Slice
The smallest piece of a chunk that works. Build it, verify it, show the owner, wait. Then the next slice.
Decision
One answered question in the manifest: the chosen answer, the rationale, the date locked, what it affects, and the rule for changing it. Written as behaviour ("the garrison buys time, never safety"), not as a feature. a ticket. Not a user story. Not a wish.
Manifest
DECISIONS.md. The one record: core goal, non-negotiables, decisions in chapters, the build timeline, the open questions, the change log. Written for the next agent, not maintained by hand. a backlog. Not a spec that gets handed off and forgotten.
Map
ARCHITECTURE.md. One page. Every domain with its purpose, entry point and config file, and how to modify one. The first thing a chunk is cross-checked against.
Design gate
The stricter pass for work where a wrong output costs money, safety or trust: an adversarial gap review of the spec before the repository exists, and a guard that refuses source writes until every finding is resolved or recorded. A review that finds nothing is a failed review. the ordinary case. A game does not get it. Every project still gets the interview, the manifest and the cross-check.
Cross-check
At every chunk boundary: the chunk against the manifest, the map, the existing subsystems, the config, the tests and the core goal, ending in Proceed yes or no. After parallel agents, one more agent gets the manifest and the whole diff.
Change Request
The only way a locked decision changes: the change, the reason, the affected areas, the risk, the required updates, the final decision. The owner decides. Yes adds a dated row to the change log. No leaves the decision standing and the work moves to agree with it.
Council
A variant of the interview for a pitch: fixed seats, each arguing one concern, run in parallel, then one verdict per element and one question at a time. Its record is kept beside the decision. a committee that decides. The owner decides. The council makes the trade-offs visible.
Hat
A named role the agent wears one at a time and announces when it changes. Creative Director, Designer, UI/UX, QA, Programmer. The Programmer hat stays locked until the others have produced an owner-approved spec.
Owner
The one person who says yes. Every slice is shown to them. Nothing is locked until they say so, and nothing is built until it is locked. a product manager relaying other people's asks.
Locked
Sealed in the manifest with a date. Superseded only by a Change Request that names its successor. Never edited in place.

What this method is not

  • Not vertical slices by department. Every domain is on the one-page map, with its config, before the first is built. A chunk is one of those domains, and it is cross-checked against all the others before the next starts. No part is designed in isolation from the rest.
  • Not requirements gathering and hand-off. The interview is the agent reading the scars and asking the owner only what only the owner can decide. Nobody collects a wish list for someone else to build.
  • Not agile sprints. A chunk is a domain and a review boundary, not a time box. There is no velocity, no backlog, no burndown.
  • Not big design up front and then silence. Decisions change, but through a Change Request that names what it supersedes, so the trail is visible and the collision is caught in the manifest, not in the code.
  • Not "the agent decides." The agent interviews, researches, argues the seats, drafts and builds. The owner locks. Nothing goes in the manifest until the owner says yes.
  • Not a promise that a machine checks every step. The kit grades every rule honestly: some are denied by a hook, some only advised, some are law text that nothing checks. The grades are in its LAW.md.

A worked example from this repo

Decision 1.5, the three towns, from DECISIONS.md, walked through the steps above. It shows why it cannot be mistaken for a department slice: nothing has been built, and the whole map was decided before any part of it.

Request
Three players, each holding a town against the undead to the north. How are the towns laid out and linked?
1 Interview
Run as a council, three seats. Verdict per element: the node graph approved, "a better-at-collecting town" redacted, player air redacted because it bypasses the chokepoints. Questions asked one at a time; the record is in records/.
2 Locked
2026-10-15. Hill, valley and forest towns, two safe edges, the third route only through the enemy. Written with rationale, what it affects, and a change rule: a new edge between hill and forest re-opens the whole graph.
3 Stakes
None. A map the group plays costs nobody money, safety or trust. The design gate is skipped.
4 Slice
One plate of the design brief drawn across the whole map, all three towns and the wild. Not one town in detail.
5 Inner gate
Screenshot saved in the repo, shown to the owner. Verdict: not accurate. Five corrections, one of them a bridge marked non-negotiable.
7 Change
Amended in place with a dated note, since the plate had not yet been called accurate. A change after that would be a Change Request.
Built so far
Nothing. No map file, no units, no triggers. The Programmer hat is still locked.

The kit's own worked example is a weather-feed bot: the interview asks runtime mode, where thresholds live, and what the tool must never do; the manifest locks fail-closed on a stale feed; the map shows feed, rules, notify and config, each with its own JSON; the agent builds the feed domain first and cross-checks that it fails closed, then rules, then notify. Six months later the owner changes a cap by editing one number in config.
